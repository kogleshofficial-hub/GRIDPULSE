# GRIDPULSE × Hack Club Stardance

GRIDPULSE is being published as an open-source technical project for Hack Club Stardance.

## Current Stardance fit

Stardance's current public guidance says the program is for high-school students aged 13–18 and that technical projects such as websites, apps, games, and hardware can qualify when they are open source. It also describes a workflow of GitHub repository → Hackatime → build + devlogs → ship → community rating. See the official Stardance site for the latest rules.

Official reference: https://stardance.hackclub.com/

## Important: existing work vs. new Stardance work

GRIDPULSE already existed before this Stardance submission. Existing code should be represented honestly as existing work. Stardance tracking and project-submission requirements must be followed for new work performed for the program; do not claim historical development time as newly tracked Stardance hours.

The goal is to continue improving GRIDPULSE with clearly attributable new work: usability, accessibility, documentation, reliability, testing, demo quality, and additional product capabilities.

## AI disclosure

GRIDPULSE uses AI assistance in its development workflow. AI can assist with implementation, debugging, research, documentation, and review, but the project owner directs the work, evaluates generated suggestions, makes product decisions, and is responsible for the final repository and deployment.

GRIDPULSE is not submitted as a one-click AI-generated site. Its source, architecture, database logic, API contracts, validation rules, UI, documentation, and deployment configuration are publicly inspectable.

## Suggested Stardance development log sequence

### Devlog 01 — Baseline

Document the existing GRIDPULSE architecture and identify the next engineering goal.

### Devlog 02 — Reliability

Improve loading, failure states, validation, and graceful handling of unavailable services.

### Devlog 03 — Accessibility

Test keyboard navigation, focus states, semantic labels, readable status indicators, and reduced-motion behavior.

### Devlog 04 — Observability

Document the evidence lifecycle: observed → validated → predicted → explained.

### Devlog 05 — Documentation

Improve the README, API reference, architecture notes, setup instructions, and judge demo path.

### Devlog 06 — Final ship

Record what changed, what was tested, what remains experimental, and the final public deployment.

## Do not claim

- Do not claim Microsoft endorsement unless Microsoft explicitly provides it.
- Do not claim a live Azure AI result when the Azure services are not configured.
- Do not claim a prediction is a confirmed outage.
- Do not claim customer, reliability, or impact statistics that have not been independently measured.
- Do not claim historical development hours as newly tracked Stardance hours.

## Submission quality target

The project should be easy for another teenager or reviewer to understand and reproduce: a public repository, a working deployment, clear documentation, visible development history, honest AI disclosure, and a concise explanation of the problem and technical solution.
